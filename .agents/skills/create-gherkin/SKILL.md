# ソースコードから Gherkin シナリオを作成する

シナリオを書く前に、対象機能のエントリーポイント、UI、状態の変化、入力検証、既存テストを確認する。リポジトリの指示と、ユーザーが指定した範囲・言語に従う。結果が変わる重要な仕様がコードから分からない場合に限り、確認する。

ユーザーまたは外部の呼び出し元から観察できる動作をシナリオにする。各シナリオで、前提条件、操作、結果を明確にする。既存テストは動作の裏付けとして使い、テストと実装が食い違う場合は実装も確認する。推測した要件、未実装のエラー処理、到達できない分岐を、実装済みの動作として記述しない。重要な不確実性はシナリオとは別に示す。

有効な Gherkin として `Feature` と、焦点を絞った `Scenario` を記述する。ステップには `Given`、`When`、`Then` を使い、条件や結果の追加には `And` を使う。ユーザーが技術的なシナリオを求めない限り、ウィジェット名、非公開メソッド名などの実装詳細に依存せず、具体的な操作と結果を書く。同じ動作を複数のデータで確認する場合に限り、`Scenario Outline` と `Examples` を使う。コードが裏付ける正常系、境界条件、失敗系を選び、同等のシナリオを増やさない。

ファイルの作成を依頼された場合は、プロジェクトで使われている場所に `.feature` ファイルを作る。既定の場所がなければ分かりやすい場所を選ぶ。シナリオの提示だけを依頼された場合は、ファイル作成が明らかに意図されていない限り、回答に記載する。依頼がなければステップ定義を追加せず、アプリの動作も変更しない。

## `bdd_widget_test` を使う Flutter プロジェクト

プロジェクトが `bdd_widget_test` を使っている場合は、そのパッケージの構文と定義済みステップに合わせる。可能なら定義済みステップを再利用し、独自ステップが必要なら生成される Dart 関数名に ASCII の英字または数字が含まれる名前にする。日本語だけのステップ名は Dart の識別子にならず、コード生成に失敗する。シナリオ名や説明は日本語のままにできる。ステップ名に英語を混ぜるか、パッケージが認識する英語ステップを使って、可読性を保つ。

`.feature` を作成しただけで実行可能とみなさない。依頼範囲に生成が含まれる場合は、既存の Makefile ターゲットなどプロジェクトの手順で `build_runner` を実行し、生成されたテストファイルを確認する。テスト実行を依頼された場合は、プロジェクトが指定する Flutter SDK で実行する。`mise.toml` などでバージョンを固定しているのに、通常の `flutter` コマンドが別の SDK を指す場合は、`mise exec -- flutter ...` のように固定 SDK を明示する。Flutter の shader 形式不一致が出たときは、テーマやアプリの動作を変更して隠す前に、実行中の framework/engine とプロジェクト指定バージョンを確認する。

提出前に、各期待結果の根拠をソースコードまたはテストで確認し、Gherkin の構文と各シナリオの独立性を点検する。生成を行った場合は生成結果も確認する。解析した範囲と、判断できなかった動作を簡潔に伝える。
